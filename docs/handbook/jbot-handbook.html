SECTION 1 · CONDUIT HUB · PERSISTENT AGENT
SYSTEM OVERVIEW
1.1

INTRODUCTION.

jbot is the Conduit durable agent (pi-durable) running as one always-on agent per hub. Underneath, it is a harness thread in a loop with tools, like any chat. What makes it an assistant is the set of parts around that loop, which decide when it runs, what it knows and what reaches the person (figure 1-1).

1.2

FUNCTIONAL DESCRIPTION.

Sources reach the hub as feeds, Conduit events, webhooks and the clock. Feeds append entries to the inbox; the heartbeat reads them and stays quiet, starts runs or tells jbot. The home thread talks with the person and delegates; runs do the work in their own conversations and report back. Every call that leaves jbot's folder passes the policy, which asks the person first (figure 1-2).

1.2.1

Two Blocks.

Block I is built (27 Oct 2026): home thread, runs, schedules, watches, memory files, approvals and push. Block II is the plan of 29 Oct 2026: feeds, the inbox, a heartbeat that calls a model only when there is something to decide, and night upkeep. Block II parts are drawn dashed, in orange.

SECTION 2 · WORK DONE AWAY FROM THE CONVERSATION
RUNS, ROUTINES, HEARTBEAT
2.1

INTRODUCTION.

Anything that is not conversation is a run: a subagent conversation with a brief, a model and effort, a tool scope and a budget, which must end by saying how much its result matters. Routines are saved triggers that start runs; the brief and the heartbeat are routines (figure 2-1).

2.2

FUNCTIONAL DESCRIPTION.

A trigger (the clock, a Conduit event, a webhook, a check-back jbot set for itself, or the person through RUN A TASK) spawns a run as a child conversation, on the model and effort set for its kind. The run works alone; an outward call it makes becomes an ask held for the home thread. Its answer's first word says how much the result matters (figure 2-2).

2.2.1

Where Results Go.

Block I posts a report the dial lets through as one line in the home thread, gives jbot a turn on it and pushes once. Block II appends every result to the inbox instead: an urgent entry wakes jbot at once, the rest wait for the heartbeat, and a quiet run leaves only its history.

SECTION 3 · WHAT IT KNOWS AND WHAT IT SEES
MEMORY AND CONTEXT
3.1

INTRODUCTION.

jbot's memory is a set of Markdown files in its own folder, which the person can open and edit from the agent page. Each turn of the home thread starts from the same assembly: its prompt and tools, the memory files, then the conversation so far (figure 3-1).

3.2

FUNCTIONAL DESCRIPTION.

The home thread writes memory as it learns, a line at a time. Content from outside (mail, the web, what a run found) cannot write: it becomes a proposal under Needs you, which the person keeps or discards. Past 16,000 characters, jbot's own lines drop out first, the diary before memory; the person's lines always load (figure 3-2).

3.2.1

Line Provenance.

Every line jbot writes ends in a hidden tag naming its thread, call and time, <!-- conduit by:home chat:… -->, which the model reads as "(noted 2026-10-29)". A line with no tag is the person's.

3.2.2

Other Chats.

jbot reads the person's other chats only when asked, through its chats tool (list, read, search). Reading one marks the thread, and an approval raised after that warns that private content may be leaving.

SECTION 4 · WHAT IT MAY DO WITHOUT ASKING
APPROVALS AND CONFINEMENT
4.1

INTRODUCTION.

jbot works freely inside its own folder and asks before anything leaves it. An outward call does not block: it is saved as an ask and returns at once, so the work carries on while the person decides (figure 4-1).

4.2

FUNCTIONAL DESCRIPTION.

The person answers an ask on its card in the thread, on the agent page or from the phone, where Allow needs the phone unlocked. The answer reaches the thread that asked as a message; that thread calls approved with the ask's id and the hub runs its saved copy of the call, once. A run's asks wait under jbot's reply to the run's report.

4.2.1

Its Own Machine.

jbot's bash runs through a helper, built with cc on first use, that applies Landlock and a seccomp filter before the command starts (figure 4-2). It costs about 1 ms a command. No helper, no bash.

4.2.2

Runs Never Approve Themselves.

A run's asks go to the home thread. They are not pushed one by one: the push for the run's report says how many wait.
