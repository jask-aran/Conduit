# Conduit v0.7.2

A client can reach more than one server, an update is one action, and a browser
can no longer be left running yesterday's build.

## Several servers

- Hold a list of servers with a token for each. An installed client rebuilds
  itself around the new address; a browser navigates, since another server
  there is another installation of this app.
- The sidebar footer names the active server and lists the rest with what each
  costs to reach. Settings → System → Servers renames, shares and forgets them.
- Servers keep the list and hand it to the next client that connects, so an
  address is entered once rather than once per device. Loopback stays put by
  default: it names a different machine on each device that reads it. See
  `docs/servers.md`.

## Updates

- Check for updates downloads, installs and relaunches in one action, with
  progress in Conduit's own window. Android hands the APK to the system.
- Settings → About names the interface, the shell and the server separately.
- A development desktop client installs beside the released one and updates
  from the Conduit server on this machine. See `docs/desktop-client.md`.

## Fixes

- Four independent faults could leave a browser on an old build: a CDN
  rewriting the service worker's cache header, nothing reloading when a new
  worker took over, an update check that reported successes as failures, and a
  page whose script failed having no way to recover itself.
- The sidebar claimed a server was empty while it was still asking.
- `/assets/` no longer needs a session, so a stylesheet cannot be answered with
  401 and render as a page without one.
- Images already sent no longer return to a composer when the chat is reopened.

## Upgrade note

No migration. The stored server and its token are carried into the new list, so
nothing is signed out.
